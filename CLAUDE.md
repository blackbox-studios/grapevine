# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**Grapevine** (throughgrapevine.com) is a **Next.js 15 (App Router) on React 19** app for Orthodox parishes and dioceses, which also ships as a native iOS/Android app via **Capacitor**.

**Invite-only, organization-scoped.** People belong to groups (a parish, a diocese) through a `Membership`. What a viewer may read is the union of the groups they hold an **APPROVED** membership in — there is no unscoped read anywhere in the API. Only a group **ADMIN** may publish into it; ordinary members read, like, and comment.

**One group is selected at a time, and it is the app's context.** The `org` store holds that selection and the group switcher changes it; the feed, the roster, invites, and every admin control resolve against it, so the same session offers a composer in a parish someone administers and none in a diocese they merely belong to. `orgId` is an optional filter on `GET /api/feed` — it can only narrow the viewer's own scope, never widen it, because the service runs `requireMembership` on it. In code a group is an **`org`** (`Organization`, `orgId`, `/api/orgs`, `useCurrentOrg`); in the interface it is always called a **Group**.

**Admission is one-directional: an admin adds people, and a person never asks to join.** There is no request, no approval queue, and nothing to accept — `MembershipStatus` is `APPROVED | REVOKED` precisely so an unapproved membership cannot be represented. This falls out of the invite-only gate: `signInWithOtp({ shouldCreateUser: false })` means someone with no account can never receive a code, so a join request would come from a person who by construction cannot act on the answer. Adding someone provisions their Supabase user, `Profile`, and an APPROVED `Membership` in one step; they simply sign in. **They are told, and which way depends on whether they have ever signed in**: admission writes an `ADDED_TO_GROUP` notification like every other event, and somebody who has signed in before is delivered it by push, while somebody who has not is sent the invitation email instead. That letter is the only thing in the app carrying a download link, and it has to exist for the same reason the gate does: `shouldCreateUser: false` means a person admitted a minute ago cannot even ask for a code, so without it they have a working account and no way to learn it exists. It carries no token and no accept route, so it lets nobody in on its own. Sent by our own server over the Resend HTTP API (`src/lib/server/invites.js` over `email.js`), which is a different path from the sign-in codes Supabase mails over the same account's SMTP: no auth rate limit, and inert without `RESEND_API_KEY`, so an unconfigured deploy admits people exactly as before. **It is queued, not sent in the request** — admission writes the `Invite` row owing a letter and `sendOwedInvites` delivers it, swept off `GET /api/notifications/unread` exactly as the sign-up reminders are, with a backoff on refusal. That is what makes a daily quota reached halfway through a roster, or a serverless instance frozen on the way out of the response, a few hours of delay instead of forty people admitted and never told. If a parish ever needs people to be able to ask, that is a new `JoinRequest` model with its own gate — **not** a third value on this enum. Putting the request half back without the entry point is what produced a roster with an Approve button nothing could populate.

**There is a real API and a real database.** The app is client-rendered (pages/layouts are Client Components) and talks HTTP to Next **route handlers** under `src/app/api/**/route.api.js`, which query **Postgres on Supabase** through **Prisma**. Only the dashboard surface in the `app` store is still in-session mock. See `.claude/skills/develop/backend-architecture.md`.

**Two build targets, one codebase.** `npm run build` produces the Node server build — the only one that can host the API. `npm run build:native` produces a **static export** in `out/` that Capacitor packages. The static target is the constraining one: it forbids middleware, intercepting routes, and route handlers, and every dynamic segment needs `generateStaticParams`. See `.claude/skills/develop/native-architecture.md`.

> **Route handlers must be named `route.api.js`, not `route.js`.** `pageExtensions` in `next.config.mjs` only treats `api.js` as a route in the Node build, which is what makes the whole `src/app/api/**` tree invisible to the static export. Name one `route.js` and the native build breaks — possibly days later, in CI. The native app therefore cannot use same-origin `/api`; point it at a deployed instance with `NEXT_PUBLIC_API_BASE_URL`.

> **Do not add `src/middleware.js`.** Vendor quickstarts (Supabase, NextAuth, Clerk) all tell you to, and it is the single most damaging thing you can do here: `output: "export"` drops middleware **silently** — no build error, no runtime error, the app just ships with no auth gate. Route protection belongs in `src/components/AuthGate.jsx`. The same applies to Server Actions, `cookies()`/`headers()`, and any native code path that depends on `src/app/api/**`. Read the "Adding a library" section of `native-architecture.md` before wiring up an auth or data SDK.

**Develop against the container, not the parish's live database.** `docker-compose.yml` runs Postgres on `127.0.0.1:54322`; point `DATABASE_URL`/`DIRECT_URL` there. It isolates **Postgres only** — Supabase Auth and Storage stay hosted, so the same accounts sign in, `dev:login` still works, and `provisionAuthUser` reuses the *existing* hosted user for an address rather than minting a new one. `npm run db:seed` and `npm run db:reset` refuse to run against a non-local host (`scripts/db-target.mjs`), because both are destructive and the only thing naming their target is an untracked variable.

**Two seeds, and the difference is not the row count.** `prisma/seed.dev.js` owns its fixture ids and deletes and rewrites them every run. `prisma/seed.prod.js` contains no delete at all: it guarantees *access* (the two admins exist, confirmed, with APPROVED ADMIN memberships in Holy Trinity Cathedral) and writes *content* only when creating a row — names, handles and the group's name are left alone forever after, because they belong to whoever set them in the app. `prisma/seed.js` only dispatches. It also asserts `platformRole: OWNER` for those two accounts, because that is access rather than content — but it is the bootstrap only, and no third owner is ever added there: `npm run owner -- <email>` grants the role, provisioning the account if the address is new.

**The database is live.** `prisma/schema.prisma` is the domain — read its header first, it explains the two decisions that carry the design. Pagination is keyset, not offset, and identifiers are snake_case in Postgres via `@@map`.

**Which pooler `DATABASE_URL` names is decided by how the target runs, and getting it wrong is an outage rather than a slowdown.** Supabase allots this database user **15 clients in session mode**, and session mode holds one of them per Prisma connection for that connection's whole life. A long-lived Node server (`npm run start`, `next dev`) is one bounded pool and fits inside that easily, so it takes the **session** pooler on **5432** and is rewarded with prepared statements and one round trip per query. **Serverless does not fit and cannot be made to.** Every warm function instance holds its own pool, nothing releases between invocations, and six instances at a `connection_limit` of five want thirty clients out of fifteen — so the pool is exhausted at a concurrency of *one or two*, which is what makes it look like anything other than a connection problem: every route calls `requireViewer`, so the first statement of every request fails at once with `PrismaClientInitializationError` / `FATAL: (EMAXCONNSESSION)`. **Vercel is serverless**, so production takes the **transaction** pooler on **6543** with `?pgbouncer=true&connection_limit=1`. The cost is real and is the reason session mode is preferred wherever it fits: transaction mode disables prepared statements and wraps every query in `BEGIN`/`DEALLOCATE ALL`/`COMMIT`, which measured ~2.5x the round trips for identical SQL. `DIRECT_URL` is **always** 5432 whatever the target, because Prisma Migrate's advisory locks and DDL do not survive a transaction pooler at all. Raising `connection_limit` is not the lever it looks like on a serverless target — it multiplies by the instance count, so it buys exhaustion sooner. See `.env.example`.

**Latency here is round trips, not queries.** Against a pooler in another region each statement costs tens of milliseconds and the SQL costs under one, so the API is written to *count statements*: `relationLoadStrategy: "join"` (preview feature `relationJoins`) collapses an `include` into one query instead of one per relation, `requireViewer` loads the viewer's memberships with the profile so no authorization check queries again, and the bearer token is verified locally against the project's JWKS with `jose` rather than by calling Supabase per request. See the "Round trips are the cost" section of `backend-architecture.md` before adding a query to a request path.

**`npm run db:secure` must follow every migration.** It applies `prisma/policies.sql`, which enables RLS and revokes the `anon`/`authenticated` grants. Supabase auto-generates a REST API over the `public` schema that answers to the publishable key compiled into our own client bundle — without that lockdown it serves every parish's posts, bypassing the entire `/api` authorization layer.

**Three authorization axes, deliberately not merged.** `Membership.role` (ADMIN | MEMBER) is per-group permission. `Profile.vocation` (PRIEST | FAITHFUL) is who someone is and grants nothing — a priest is usually their parish's admin but need not be, and an admin need not be a priest. `Profile.platformRole` (NONE | OWNER) is the subscriber's authority over the *app*: the right to create groups and delete the ones they created. See the next paragraph.

**An OWNER is whoever paid, and ownership is the boundary of a subscription — not a master key.** A priest buys Grapevine, is granted OWNER, and can then build: `POST /api/orgs` creates a group and `DELETE /api/orgs/:orgId` destroys one *he* created (`Organization.createdById`, confirmed by echoing the group's slug). He has **no standing at all** in a group he did not create — not the feed, not the roster — so he can be an owner of his parish and his catechumen circle while remaining an ordinary member of the diocese everyone reads. `requirePlatformOwner` is called in exactly two places, both in `orgs.service.js`, and neither reads anybody's content; `requireViewer`'s membership scoping is untouched by this column. His authority *inside* a group he created is a real APPROVED ADMIN `Membership` written by `createOrg` and protected from removal by `updateMembership` — materialized rather than derived, so every read path still asks the one question it always asked, and no admin he later adds can take the group out from under him. Creating one is `<OrgCreator/>`, opened from a **New group** row at the foot of the group switcher that is drawn only for an owner — a dialog on desktop and a sheet on mobile, and not a route because nobody links to a form that creates something. Deleting is the danger zone at the foot of `/group/info` — collapsed until asked for, armed only once the group's name is typed, and drawn off `canDelete`, which the server composes from `canDeleteOrg` so the button cannot appear for an action that would 403. The seeds assign an owner too — `seed.prod.js` gives Holy Trinity to Fr. Alexander, whose parish it is, and repairs the column on a row that predates it. Robert administers the Cathedral and can publish, invite and rename; retiring it is Fr. Alexander's alone, because `createdById` holds one id and a boundary two people can cross is not a boundary. The role is **not assignable through the app**: `npm run owner -- <email>` grants it (provisioning the Supabase user and `Profile` if the address is new, since the app is invite-only), `npm run owner -- --revoke <email>` takes it back, and `npm run owner` lists every owner with the groups they created. That script is the seam a billing webhook plugs into; it must not become a route. Full rationale: §11 of `backend-architecture.md`.

**Not every group is a parish, and the app no longer has an opinion about which is which.** `OrgKind` (`PARISH | DIOCESE | MONASTERY | GROUP`) grants nothing, nothing branches on it, and **no screen renders it** — every group behaves identically, so the create form does not ask and `updateOrg` refuses to change it. New groups default to `GROUP`. The column stays because the rows that predate it genuinely are what they say, and it is the only place that is written down.

**Somebody else's profile is a card, and following them is a list — not a permission.** Tapping a handle anywhere a byline appears opens `<ProfileCard/>` — a dialog on desktop, a sheet on mobile — mounted once by the shell, with whose card is open held in the `profile` store as `openHandle`. `<HandleLink/>` is the one shared trigger behind every byline. A card rather than a route because it is glanced at and dismissed: a handle tapped inside an open post must not take the post down, and Android's back gesture should close the card rather than unwind a history entry. **Three tabs hugging the card's top edge** (the shadcn `<Tabs/>` segmented control, full width and square-cornered so the container's radius does the rounding, laid out as two grid rows so the bar is fixed chrome and the panels are the scrolling body): *Info* carries the identity — picture, name, handle, a colour-hashed `<Badge/>` for the vocation, and one button that is **Follow** or **Edit profile** on your own — over a list of labelled rows, the label left and the value right with a hairline between (patron, name day, ordination, each absent rather than blank); *Followers* and *Following* carry the lists. **Which tab it opens on is part of opening it** — `open(handle, tab)`, held as `openTab` — because a tapped handle asks to see the person and a tally names a list, and answering the second with *Info* makes the reader tap twice for what they already pointed at; `close` puts it back to `info` so the same tally tapped twice still registers as a fresh open. Putting the bar above everything is what gives every tab the same full height. **Both lists load when the card opens**, not on the tab that shows them — the `follows` store holds a slot per direction and fetches the pair in parallel, so a flip between tabs is a re-render rather than a round trip, and all three panels can stay mounted and cross-fade. The follower lists are tabs rather than a second modal because walking from a person to their followers to one of *those* people is the whole point of the surface, and a modal stack made every step a layer to dismiss; tapping a row calls `openProfile` again and the card stays up. **Your own card never shows a skeleton**: `/api/me` carries the follow tallies so `viewerProfile` can seed it synchronously — the load runs in a *layout* effect and the skeleton sits *outside* the tab crossfade, which is what makes that seed genuinely invisible. **`Follow` grants nothing**: `readableOrgIds` does not consult it and must not start, or one parish's posts reach somebody with no membership in it. It is kept for direct messaging. Who you may *see* is `visibleProfile` — one shared APPROVED membership, 404 otherwise, so a handle alone never confirms an account exists. The card lists **no groups** and wears **no check**: naming a parish to a non-member is the leak a future join-request feature would have to be designed around first, and the check means "administers the group you are reading this in", which a card is not read inside — the vocation stands in its place. If a `JoinRequest` model ever lands, note what it is: the asker is already provisioned and signed in, so it does not reopen `shouldCreateUser: false`, and it is still not a third `MembershipStatus` — see the admission note in `prisma/schema.prisma`.

**Direct messages are end-to-end encrypted, and the server is a relay that cannot read them.** The Signal protocol — X3DH plus the Double Ratchet — is implemented in `src/lib/crypto` from the published specifications at signal.org rather than vendored: Signal's own JavaScript is GPL-3.0, which is copyleft this app cannot take on, and the specs are public documents whose pseudocode the protocol files follow section by section (`primitives.js` for the curve and KDF layer, then `x3dh.js`, `ratchet.js`, and `engine.js` for sessions and envelopes, over the device-local key and plaintext store in `storage.js`). `npm run crypto:test` exercises the protocol through direction changes, out-of-order delivery across a ratchet step, tampering and a serialization round trip, and then drives `engine.js` itself over the device store — session reuse, replay, a skipped target, a corrupt envelope, prekey top-up — which is where the risk sits, since the protocol files transcribe a spec and the slot logic around them does not. Run it after touching any of them. The one declared deviation is the identity key, which is **Ed25519 with the Montgomery form derived for DH** rather than Signal's XEdDSA over a Curve25519 key — same key doing both jobs, standard signatures instead of a hand-rolled scheme, and the alternative X3DH §2.2 itself names.

**Every installation is a device, and a message is encrypted once per device.** `CryptoDevice` holds one install's public bundle (identity key, signed prekey, a one-time prekey pool that `bundlesFor` consumes under `FOR UPDATE SKIP LOCKED`); `Message` has **no body column at all**, only `MessageEnvelope` rows, one per recipient device *and* one per other device of the sender, which is what lets somebody's phone and laptop both read what either sent. Private keys and decrypted plaintext live only on the device, in Capacitor Preferences on native and localStorage on web — so **there is no backup and a reinstall is a new identity**: it sends and receives from that moment and cannot read what came before, which is Signal's own trade and the reason a bubble can render as "from before this device". Keys are registered from the *shell* (`useMessagingBoot`) the moment an adult viewer is in, never on first opening the inbox, because being reachable is the half the other person depends on. The push banner carries a name and never a word of the message, since the server has only ciphertext; a request from a stranger carries neither.

**Who may write to whom is the membership graph, and 18 is a floor.** One shared APPROVED group — `visibleProfile`'s boundary a second time, re-checked on every send so a revoked membership bites here as it does on the feed — which is what lets somebody message a person from another parish through the diocese they both belong to. Both parties adult by `Profile.birthday` (`isAdult`, in `lib/utils.js`, shared by the server gate and the chrome that hides the entrance): a minor sees no send icon, cannot be found in the contact list, and is refused by every endpoint — and a **null birthday is not an adult**, because the one feature with an age floor must not fail open for the person nobody recorded. `MessageBlock` freezes a pair in both directions. Erasure is unchanged in shape and lighter in fact: the cascade takes the account's keys and envelopes, and there is no plaintext on the server to take.

**A first message from someone you do not follow is a request, not a message.** `ConversationParticipant.acceptedAt` null means the thread renders blurred — face behind a blur in the row and the header — with Block / Delete / Accept in place of the composer, and `sendMessage` refuses a reply until it is set, which is what makes the tap mean something. Following somebody is standing permission to be written to and skips the gate entirely, and it is the only thing `Follow` grants anywhere in the app. The promise the server keeps is that **nothing tells the sender the request was seen**: accepting is the first observable fact.

**The inbox is a page and a thread is a slide route.** `/inbox` lists conversations newest-moving first, iMessage's shape — avatar, name, decrypted snippet, the time and a chevron, a blue dot in the gutter for unread — and `/inbox/c/:id` is a `slide: true` runtime route that pushes in over it, so Android's back gesture returns for free and a tapped push banner from a cold launch lands on the same surface. **Above the `md` breakpoint it is not an overlay at all**: it is `inline`, the third presentation, and the URL selects which conversation the inbox's right half holds rather than opening anything over it, so every entrance goes through `useRouteOpener` rather than `openSlide`. Two animations carry the feel and both are in `Conversation.jsx`, whose `<Rail/>` owns them (`<ConversationView/>` is only the slide wrapper): **scroll lag**, where one clamped scroll-velocity value is followed by every bubble through its *own* spring so rows shear out of phase and settle, and **the send**, where a new bubble springs from the composer's corner while `layout` eases the rest up — and only genuinely new rows animate, since a history that assembles itself is a loading screen. Unread rides the notifications poll (`unreadConversations` on `/api/notifications/unread`), so messaging adds no request to the boot path.

**Offering to turn notifications on is one component, because it is not one call.** `<PushOffer/>` owns the whole three-state rule — a platform with no push at all, permission already granted, and permission already *refused*, where the tap has to open the OS's own settings because a spent prompt cannot be shown again — and renders nothing in the first two cases, since an offer to turn on what is already on is a control that does nothing. `usePushPermission().turnOn` decides prompt-versus-settings; the component decides when to say nothing and what the button is called. Account settings makes the standing offer; the sign-up surface makes it the moment somebody asks to be reminded about a date. **Turning "Remind me" on runs that same procedure**, because asking to be reminded is asking for a notification — a reminder the device will never deliver is the failure that matters, and finding out on the morning of the shift is the whole thing gone wrong. The row still lands in the panel either way, which is what the offer says rather than reporting an error.

**Erasure is a script, not a screen — because nobody can create an account here, and self-deletion would be a one-way door.** Play's account-deletion requirement is conditional on a user being able to *create* an account in the app, and `signInWithOtp({ shouldCreateUser: false })` means none can; the mandate does not reach this app. It is also the wrong control for it: membership is invite-only, so a parishioner who deleted themselves could not return without an admin re-provisioning them, which turns a mis-tap into someone else's afternoon. A parish is a small group of people who can simply ask. So `npm run erase -- <email>` reports what would go and changes nothing; `--confirm` does it. What the script exists to prevent is that request being answered by hand in a database console, because **two departures leave states nobody inside the app can repair** and neither is visible while looking at one person's row: an **owner with groups they created**, since `Organization.createdById` is `SetNull` and `canDeleteOrg` compares against it — erasing them makes those groups permanently undeletable rather than merely ownerless; and the **last admin of a group that still has other members**, the same hole `updateMembership` closes by refusing to let an admin demote themselves. A sole admin of an *empty* group passes: there is nobody to strand, and "promote a successor" is not an instruction one person alone can carry out. `Profile` is the root of every cascade in the schema, so one delete takes the memberships, posts, comments, likes, follows, notifications, device tokens and messages with it; the Supabase credential goes **second**, because `requireViewer` refuses a token with no profile behind it, so a failure between the two leaves someone who cannot use the app rather than someone still posting to a parish feed. GDPR Art. 17 is the standing reason this exists at all, and it is independent of any store's policy. The Data safety form still wants a public deletion-request URL reachable by somebody who cannot sign in; that is a marketing-site page, not a route here.

**A store reviewer is provisioned, never self-served, and the door closes after.** The app is invite-only by construction, so `signInWithOtp({ shouldCreateUser: false })` means the person Google or Apple sends can neither sign up nor be sent a code. `npm run reviewer -- <email> --org <slug>` creates an ordinary APPROVED MEMBER and stamps `onboardedAt` so they land on the feed instead of on `/welcome` being asked for a patron saint. `POST /api/auth/review` is how they get in without an inbox, and what it *cannot* do is the design: it **never mints a session**. It compares the address against a compile-time constant, compares the code with `timingSafeEqual`, and hands back Supabase's real current OTP for that one address — the ordinary `verifyOtp` flow then performs the sign-in, so Supabase still authenticates and there is no second way to obtain a session anywhere in the app. Unset `REVIEW_EMAIL`/`REVIEW_OTP` and it 404s, which is every normal deploy. This is a bounded exception to the rule in `dev-login.mjs`'s header, and it holds only because of those two properties; widening either turns it into the backdoor that file refuses to be. Closing up is two steps on purpose — unset the variables, then `--revoke` — because a resubmission needs only `--org` again.

**The parish's week is one page, and it is two tabs because it is two different kinds of fact.** `/events` shows the group's own calendar and its sign-up sheets over one subject: what is happening here, and what it needs hands for. The calendar leads, because it is the tab worth opening when nothing is being asked of you. Both tabs are scoped to the **selected group**, with no id in the URL, like `/group`.

**The month and one of its days are two surfaces, never one screen with a panel.** A grid with a day's events under it is two screens stacked, and on a phone it is a grid you scroll past to reach what you just tapped — so tapping a square *goes* to that day, which has a back arrow, its own prev/next, and a cross-fade between days. **Today is the only square the grid marks**: tapping navigates, so nothing is ever "chosen and still here", and a fill left behind would be marking history rather than state. **Today** as a button appears only once the reader has paged away from this month, since on it the button does nothing. The grid draws **two concentric rings** — inner for the parish's calendar, outer for a sign-up, filled rather than tinted when the viewer is on that date themselves — and is always six rows, so paging never changes its height.

**Months are cached, and their neighbours are fetched behind them.** A calendar is read by moving through it, and a skeleton on every move makes a month feel like a page load — so `calendar.months` keys resolved windows by "YYYY-MM", paging is a lookup before it is a request, and opening one month warms the two either side. One step ahead in each direction, not more: each step warms the next, so paging is instant from the second move on, where a deeper window would be four requests on boot to serve a reader who mostly looks at this month. The cache is per group and is emptied on a switch. The month is **warmed from the shell**, not from the surface: `useCalendarWarm` claims the selected group's current month on an idle moment at boot and on a switch, so the tab opens on a grid. A calendar warmed by the calendar would be warmed a frame late, since an effect runs after the paint that already showed the skeleton.

**The day is a linear rail of its hours, with the empty stretches folded away.** Hours are drawn only where something is in them, and a run of nothing over 90 minutes becomes an unlabelled dashed rule — the hour marks either side already say how much was skipped, and a number there would be the one piece of text on the surface describing an absence. Runs whose padding meets are merged, so a contiguous rail is never cut by a rule with nothing to mark. A typical Sunday draws seven hours instead of twenty-four, which is what buys the rail room to be readable: an hour is 72px, and no block is drawn shorter than 54, because a half-hour service at true scale is not tall enough to hold its own title without the text colliding. **Tapping a sign-up block opens the sign-up surface then and there** — the block carries the slot's own shape, so there is no rota to load behind it, and the same surface gives a place up if the viewer already has one.

**A parish already keeps its calendar somewhere, so Grapevine reads it rather than owning it.** `Organization.calendarUrl` holds a public Google Calendar exactly as an admin pasted it, set on `/group/info` beside the name and the picture; `icsFeedUrl` in `lib/utils.js` normalizes the three things a person might paste (the `embed?src=` link, the `.ics` feed, the calendar's bare address) and is the same function the group form validates with and the server fetches through. It is a **feed, not an embed**: `lib/server/ical.js` parses iCalendar and expands recurrence, which is what lets a parish service and a sign-up slot share a square on one grid — an iframe is a sealed box the app could not read. Importing those events into our own tables was rejected for the reason that matters: it would make Grapevine a second place every service has to be corrected. The fetch is cached per feed for ten minutes, is guarded against pointing at the server's own network (https only, no private addresses after DNS resolution, no redirects, capped body and timeout), and **every failure degrades to no calendar rather than to no page** — the sign-ups half is this app's own data and must not go down with somebody else's.

**A sign-up sheet is a rota, and its dates are rows.** `SignupSheet` is "Coffee hour", `SignupSlot` is one dated opening on it with its own `capacity`, and `SignupClaim` is a person in it. The slots are **materialized, not a recurrence rule evaluated at read time**, because the third sentence of every real conversation about a parish rota is "no soup kitchen on the 24th, and we need six on the 31st" — a rule cannot hold an exception without a second table of exceptions, and a claim has to point at a row that exists. `generateSlots` keeps the rule's convenience: the create form asks *which days* (a weekday repeated, or a span of dates) and *whether a day is one shift or several*, and those two questions cover all three rotas the Cathedral actually runs — coffee hour every Sunday for one person, the kitchen every Saturday for four, and the Do Division Festival's car park in two-hour shifts from 4pm to 10pm over one weekend. It steps **dates** and applies the time of day in `SignupSheet.timezone`, which is the whole reason that column exists: adding seven days to an instant walks an hour off on the Sunday the clocks change. Publishing is ADMIN of the group (the same permission as a post — a rota is the parish asking); taking a slot is MEMBER (the same as a comment). Capacity is settled by a **locked read inside a transaction**, so two people taking the last place cannot both succeed; `@@unique([sheetId, startsAt])` plus `skipDuplicates` is what makes "add another twelve Sundays" idempotent rather than a way to get two coffee hours on every Sunday.

**`onBehalfOf` is why a claim is not just a join row.** The Orthodox Christian Fellowship signs up for coffee hour and sends whoever it sends, so the calendar reads "OCF" where it would otherwise read one student's name — but one member still claims it, because somebody has to be answerable and the reminder has to reach an inbox. Free text rather than a foreign key: most of the bodies a parish's volunteers stand for are not groups in this app, and making them be one would mean creating a Grapevine group before you can bring biscuits.

**A rota about food is a rota about the fast, so it can say so.** `SignupSheet.showFasting` is the creator's switch — asked when the rota is published and editable in edit mode — and it puts the day's rule at the top of the sign-up surface: the five glyphs of the Daily Read, lit for what is permitted, over the same rule written out. Per sheet rather than always on, and off by default, because the same table runs the cleaning rota and the car park, where the day's rule says nothing at all. The rule is **not stored on the slot** and must not be: it is a fact about a date, identical in every parish, so a copy on a row would be a second place the calendar of the Church has to be corrected. It is read from `GET /api/fasting?date=` — the almanac half of `/api/prologue` split out, so taking four Sundays does not pull down four days of somebody else's licensed corpus to print one sentence, and both halves share the server's `observances` cache. On the client the `fasting` store keys rules by date and keeps them for the session, and a rota reads its nearest few dates on an idle moment (`useFastingWarm`), so opening a date is a component that renders rather than a request that has to come back. Every failure degrades to no strip, exactly as the Daily Read's does, because neither surface is about the fast. `<Fasting/>` owns the glyphs and the sentence for both, and the sentence's subject is a parameter: a form headed *Sunday 12 October* saying "Today is a fast" is a false sentence.

**Publishing a rota tells the parish.** A fan-out over every approved member but the admin, exactly as publishing a post is and for the plain reason that a rota nobody knows about gets no volunteers. The rows go in the same transaction as the sheet and the push follows the commit unawaited, which is the rule the whole notification layer is built on. `Notification.signupSheetId` is a second nullable link beside `signupSlotId` because the two happen at different granularities — a reminder and a cancellation are about **one date**, a publication is about **the rota** — and pointing a publication at the sheet's first slot would read fine until an admin removed that date and the cascade took the announcement with it.

**Cancelling a date is not deleting it, and that distinction belongs to the volunteers.** A deleted slot drops the people on it having told them nothing; `canceledAt` keeps the row, notifies everyone in it, and strikes the date through. Deleting is refused once anybody has signed up. **Reminders are rows** (`SignupReminder`, one per claim per offset — a week out and a day out, `SIGNUP_REMINDER_OFFSETS`), written at claim time and claimed with a conditional update before they are sent, so a schedule that fires twice cannot nudge anybody twice; anything more than six hours overdue is retired rather than delivered, because a nudge about a shift that started this morning is not a reminder. `SIGNUP_REMINDER` and `SIGNUP_CANCELED` are the two notification types with **no actor** — a clock did the first and the parish did the second — so the panel draws a glyph rather than a face and a whole sentence rather than a handle and a predicate. **Delivery does not depend on a cron.** `sweepDueReminders` runs off the back of `GET /api/notifications/unread` — the app's closest thing to a clock, asked by every client on boot, on every foreground, and on a thirty-second poll where push cannot reach — throttled to once every few minutes per process, never awaited, and idempotent against other instances because `sendDueReminders` claims its rows before it uses them. Same argument as `topUpRecurring`: a feature that quietly does nothing until somebody finds an environment variable is broken for everybody who did not. `POST /api/signups/reminders` (gated on `REMINDERS_SECRET`, 404 without it, driven by `npm run signups:remind` on a cron) is the *punctual* path and buys minutes rather than function. It is an endpoint rather than a script because sending writes a `Notification` **and** pushes to FCM, and both live behind `import "server-only"`, which a plain Node process cannot resolve — a script would need a second copy of each.

**Administering a rota is a mode of the sign-ups tab, not a page.** A priest looking at Sunday and noticing nobody has signed up should be able to add a place from where he is standing, not go round by the group settings and find the rota again. The list is identical either way — same rotas, same dates, same order — so what differs is only what each date *offers*: a Take button, or a capacity field and Cancel. One circular icon button sits on the end of the tab bar, drawn for an admin of the selected group and defaulting to View. It is a verb rather than a pair of named halves: a pencil that offers the change and an eye that puts you back to reading (a tick would promise a Save this has no Cancel for, since an edit is already saved by the time you look away), with the state carried by the button's own form (`outline` on offer, `default` once you are in it) rather than by a word, because there is nothing to choose between here and a segmented control spent the width of two labels out of a row that is already a full-width tab bar. It stays there on both tabs rather than appearing with the sign-ups one: a page-level control belongs in the page's top row, and one that comes and goes is one somebody has to go looking for. The group tree's **Manage events** row turns edit mode on and navigates there, which is the only other entrance. `useEventsView` re-checks the role rather than trusting whoever set the mode, and none of it is a control — `requireMembership(..., { role: "ADMIN" })` is.

**A rota is a place you go, and it has a URL.** `/events/s/:sheetId` is the app's first `slide: false` **runtime route**, which is the shape that split exists to express. Three things want to point at a rota and none can point at store state: a priest posting "sign up for coffee hour" and linking it, a reminder opening the rota it names, and a tapped push banner arriving from a cold launch. It has no page file (a cuid cannot be enumerated for `generateStaticParams`), is reached with `pushRoute`, and is substituted into the page slot by `<RuntimeRoute/>` — so a tap from inside the app and a cold load of the same link render the same component. The prefix is nested under `/events` deliberately: `isRouteActive` is a segment-safe prefix test, so a rota keeps the Events tab lit where a sibling `/s` would leave the rail dark. Android's back gesture returns from it (`useBackHandler`), and the back arrow is a real navigation rather than `history.back()`, because a cold load has no entry to unwind.

**Tallies read as empty, not as full: "0 of 4 taken", never "4 of 4 left".** A rota is published because it needs people, and the number that moves somebody is the one that is still short. "Full" replaces the count outright at the top, because "4 of 4 taken" is a sum somebody has to do to learn there is nothing to do.

**Opening a rota is not a request.** `GET /api/signups` ships every sheet **with its dates**, so the `sheet` store promotes the listed rota synchronously and refreshes behind it — the same order `post.load` follows with the feed's cached row. Two things fall out of that: nothing on this surface is a stored tally (every number is counted off the slots in hand by `summarize`, so a claim moves a row's sentence by replacing one slot and no count can disagree with the dates it counts), and "what have I signed up for" is derived from the rotas already on screen rather than being a second collection on the response.

**Most rotas have no end, so that is the default.** A standing rota — the kitchen every Saturday — has no answer to "for how many weeks", and asking is asking a priest to pick the date the parish stops feeding people. So a weekly rota is created with `repeats` on and the week count only appears when it is turned off; a span of dates is the other kind by definition and is not offered the toggle. "Ongoing" is real rather than a large number: `topUpRecurring` refills the rota to `SIGNUP_HORIZON_DAYS` **whenever it is read**, by repeating the last day already on the sheet a week later at the same wall-clock time. It stores no rule — the rows *are* the rule, so an admin who moves the rota to ten o'clock has moved every future one — and it is a write on a GET deliberately: a deploy with no cron must not quietly run out of Saturdays, and `@@unique([sheetId, startsAt])` plus `skipDuplicates` makes concurrent readers idempotent. A rota that *does* finish (the festival's weekend) sinks below the standing ones and reads **Finished** rather than being deleted, because who did what is worth keeping.

**One event kept in two places is shown once.** The Cathedral's Google Calendar says "Cathedral's Kitchen" because it happens; the sheet says "Cathedral kitchen" because it needs hands. `mergeCalendar` folds them on **same day, same normalized title** — `normalizeTitle` folds case, a possessive and a leading "the", and deliberately nothing else, because a fuzzy matcher that quietly folded "Vespers" into "Vigil" would hide a service and no priest could predict or correct it. A merged entry is the **sign-up** (the half a reader can act on) wearing the union of the two spans and the parish event's location. It does *not* say it was merged: to the reader it is one thing happening on one day, and that the parish files it under two names is our problem rather than theirs. A parish event is consumed by at most one slot, so a rota split into six shifts does not swallow it six times. `SignupSheet.calendarTitle` is the escape hatch for the pair no rule could guess, and pointing it at a name nothing uses is how merging is switched off for one sheet. It is **collapsed behind a disclosure** in edit mode and labelled as rare, because most sheets are for something internal that is on no public calendar at all — an empty box under a heading reads as a question somebody ought to answer.

**Everything a person may change about themselves is one form, at `/settings/info`.** The avatar picker, first and last name, @handle (live-checked against `/api/me/onboarding/handle` through the shared `<HandleField/>`, the same control orientation uses), display name, patron saint, name day, ordination date, birthday and a read-only email — all of it one `PATCH /api/me`, which is a genuine partial update so the picker and the form cannot clear each other. `birthday` and `email` are collected there and never published: they are absent from `projectProfile` entirely, which is what the padlock beside their labels means. The two exceptions are **`vocation`**, the admin's to set because the check and the roster's sort order derive from it, and **`email`**, which is Supabase's credential rather than a profile field.

**A person is addressed by the name they typed; the blue check is composed.** `Profile` holds `firstName`, `lastName`, `patronSaint`, `displayName`, `handle` and `vocation`. `displayName` is the string a byline, a follower row and a push banner all print, and it is **manual** — the app composes no addressed form at render time, because there is no correct composition: a patron saint is the saint written as the Church writes him, so "The Right-Believing Prince Alexander Nevsky" is a correct value in that column and prefixing it with a rank produced push banners reading "Priest Right Believing Prince Alexander Nevsky". `suggestDisplayName()` in `src/lib/name.js` is the one place a rank and a name are still joined, and it writes into an editable field (a step at `/welcome`, a box at `/settings/info`, both shown only to `RANKED_VOCATIONS`) rather than onto a screen; `VOCATION_TITLE` in `constants.js` is its only consumer and the only place a title is written down. `displayName()` falls back to the legal name and then to `@handle`, so a layman never has to answer the question. There is **no `fullName` column and no `verified` column** — a stored display string cannot serve the feed and the roster (which sorts on the surname) at once, which is why `fullName()` ignores `displayName` entirely, and a profile-wide verified flag could disagree with the admin role it claimed to describe. The check is derived per post from `Membership.role == ADMIN` in that post's group, so the same person can carry it in the parish they administer and not in their diocese. `RANKED_VOCATIONS` (READER through BISHOP — the ranks a name is conferred with) is deliberately a **separate list** from `CLERGY_VOCATIONS` (DEACON and above), which answers who was *ordained* and therefore who is asked for an ordination date. Name, handle and birthday are collected once, step by step, at `/welcome`, along with the vocation-dependent questions above.

Not a monorepo — the whole project is a single npm package rooted at the repo top level. Next.js App Router, Zustand, `motion`.

## Copy

**No em dashes in anything a reader sees.** Not in labels, buttons, placeholders, descriptions, validation messages, toasts, error strings, the legal documents, or store-listing text. The reason is not typographic: an em dash mid-sentence has become the tell that a machine wrote the line, and a parish app asking people for their birthday cannot afford to read as generated. Use a full stop, a comma, "so", or a pair of brackets — every one of them is clearer anyway, because an em dash is usually a sentence that has not decided what it is.

Two things this does **not** cover. **Code comments are exempt** and the repo's are full of them; nobody outside the team reads a comment, and the house style there is deliberate. And `"—"` standing alone as an **empty-value glyph** in a table or a settings row (`{current?.name ?? "—"}`) is typography rather than prose, so it stays.

Developer-facing throws and `console` lines sit with the comments: they are read in a stack trace, not by a parishioner.

## Frontend architecture

- **Every form is `react-hook-form` + `zod` through the `Form` primitives in `components/ui/form.jsx`** — `<FormField>`, `<FormLabel>`, `<FormControl>`, `<FormDescription>`, `<FormMessage>`. Not a preference: those wrappers own the `htmlFor`/`id` pairing, `aria-describedby`, `aria-invalid` and where the error message lands, and hand-rolled `<label>` + `useState` markup reproduces the visible half while silently dropping the accessible one. Deviate only where the primitives genuinely cannot express what a screen needs, and say why in a comment — `<ComposeForm/>` is the one case, and it still uses `<Form>`/`<FormField>`/`<FormControl>`, departing on a single point (validation toasted instead of `<FormMessage>`, because borderless writing surfaces have no box to hang a message off). "Simple enough to do by hand" is not a reason. See the Forms section of `frontend-architecture.md`.
- **Strict layering: API → store → hook → component.** `src/lib/api.js` is the only thing that fetches, stores are the only thing that calls it, and hooks are the only thing that touches a store. `api.js` also attaches the Supabase bearer token per request and signs out on a 401. The `feed`, `post`, `comments`, `profile`, `follows`, `auth`, `members`, and `notifications` stores are API-backed (`{ items, nextCursor }`, cursors opaque); only `app` is still in-session. `org` fetches nothing at all — it holds the selected group and the switcher's open state, and the list of groups it selects between comes from the viewer.
- **The list and the open post are separate stores.** `feed` owns the paginated list; `post` owns the open post and every write to a post (likes, comment tallies), applying each one to both its own copy and the feed's row through `patchPost` — otherwise a heart filled in the overlay empties again when it's dismissed. `comments` → `post` → `feed` is the dependency direction; keep it that way. `profile` → `follows` is the same shape a second time: `profile` owns the person a URL names and every follow write, `follows` owns the rows of the list open over them, and the arrow is one narrow `patchRow`. `profile` → `notifications` is that arrow again, `patchActor`, because the panel's **Follow back** is the same write on a third surface.
- **A comment thread is ranked, not chronological — one stored number, `Comment.score`.** Your own comments are pinned above the body (that part is a promise, not a weight), and the body is recency plus likes plus a boost for the post author's own replies, all denominated in **hours** so every weight is a sentence about time: a like is worth six hours of freshness, and each *doubling* of likes buys another six, so fifteen likes hold the top of a quiet thread for a day and a hundred get forty hours rather than six hundred. It is a **column** because the time term scores the comment's *absolute* timestamp rather than its age — the trick from Reddit's `hot` — which makes the value time-invariant, so it never goes stale on its own, it moves only inside a write we were already making, and `(post_id, score DESC, id DESC)` keeps a page an index range scan with a `(score, id)` keyset cursor. Not Reddit's `best`: the Wilson interval needs a denominator, and there are no downvotes here. Not Instagram's: that is a per-viewer learned score, which cannot be a column and which earns its keep on a thread of forty thousand strangers rather than one with eleven people who all know each other. The formula and every reason for it are in the header of `src/lib/rank.js`, which is the only thing that may compute it; re-tuning the weights re-ranks nothing on its own, so `npm run comments:rescore` is the second half of changing them.
- **Post detail is fetched at runtime, by id.** Opening a post promotes the feed's cached row synchronously — so the photo the reader just tapped paints on the first frame with no skeleton — then refreshes it from `/api/posts/:id` silently in the background. That's what lets post ids be unknown at build time, which the static export requires.
- **No simulated latency on anything with an endpoint.** Reads hit Postgres, and a warm feed page answers in ~0.3s, so a floor on an API-backed store would now be the slowest thing in the request. `MOCK_LATENCY_MS` survives for one consumer — the `app` store, whose dashboard surface has no endpoint yet and would otherwise resolve in zero milliseconds and flash its skeleton — and stores must not add a `mockDelay` floor of their own.
- **Auth is Supabase, an emailed one-time code** (6 digits here — a dashboard setting, mirrored as `OTP_LENGTH`; a fresh Supabase project defaults to 8, so the two must be set to agree). A code rather than a magic link because a Capacitor WebView has no origin to redirect back to. **The Magic Link email template must contain `{{ .Token }}` or no code is ever sent**; the one this project sends is checked in at `supabase/templates/magic-link.html` and carries no link at all. Mail goes out over **Resend, from `no-reply@throughgrapevine.com`** (credentials in the Supabase dashboard, DNS records in `.env.example`). Sending is capped at **30 messages/hour under Authentication → Rate Limits** — raise it before onboarding a parish, because a roster added in one sitting is a burst of first sign-ins and the 31st gets `429 over_email_send_rate_limit`. `SEED_ADMIN_EMAIL` / `SEED_MEMBER_EMAIL` should still point at inboxes you control, since signing in means reading a code out of one. See `.env.example`. Invite-only is one option: `signInWithOtp({ shouldCreateUser: false })` means an address with no account can never be sent a code. Supabase owns the *session*; `GET /api/me` owns the *viewer* (profile, vocation, role, groups) — `loggedIn` means both are in place. Route protection is client-side (`<ProtectedGate>` / `<PublicGate>` in `src/components/AuthGate.jsx`) and role gating is `<Privileged>` in `src/components/Auth.jsx`, but **both are presentation** — real enforcement is `requireViewer` / `requireMembership` in `src/lib/server/auth.js`. See `.claude/skills/develop/auth-architecture.md`.
- **A session ends only when the viewer or an admin ends it.** Grapevine signs someone in once on a device and stays that way, like every social app and unlike a bank: a parish feed is glanced at between other things, and a login screen in front of it teaches people to check it less often. The short-session posture defends a shared terminal holding money; this is a personal phone, invite-only, where the worst an unauthorized reader does is read posts. Revocation carries the security instead — `Membership.status` is read from the database on every authorization decision, so removing someone bites on their next request however old their session is. Nothing transient may end a session: only a 401 that has already survived a forced `refreshSession()` reaches `expire()`, `sessionToken()` reports "session on disk, no token right now" as `stale` rather than as signed-out, `init()` keeps the cached viewer when `/api/me` fails transiently, and on native the session lives in Capacitor **Preferences** (`UserDefaults`/`SharedPreferences`) because a WebView's `localStorage` is website data the OS may reclaim. Token refresh follows the app in and out of the foreground via `appStateChange`. See the "Staying signed in" section of `auth-architecture.md` before touching `lib/api.js`, `lib/supabase.js`, or the auth store's `init`.
- **A photo arrives; it does not appear.** Every image the app draws goes through `<Img/>`, which holds it at zero opacity until `load` and fades it in over 300ms. A decoded image is painted the instant it is ready, and against a box that is already the right size that reads as a flash rather than as a photograph landing. One thing makes it invisible where it should be: an image the browser already has is detected in the ref (`complete` plus a non-zero `naturalWidth`, which is also what separates a cached hit from a failed load) and drawn at full opacity with no transition at all, so the photo tapped from the feed into the open post is up on the first frame. A failure is shown rather than held back, since the alt text is what the reader has left.
- **A URL typed into a post is a link, and it is the only thing in the app a reader can copy.** `<Linkify/>` tokenizes every body surface (the feed caption, the post, a comment) with `linkTokens` and renders the URLs as real anchors, which is enough for the tap: Capacitor's navigation delegate cancels any navigation off the app's origin and hands it to the OS, so a link opens in the phone's browser with no plugin involved. The **hold** is the app's own popover, because the packaged app suppresses `-webkit-touch-callout` everywhere and Android's WebView never had a link menu at all: **Open in browser** and **Copy link**, drawn from the same `<MenuItems/>` a held comment uses, with `ios.allowsLinkPreview: false` keeping WebKit's own menu off the same gesture. Selection stays off across the app, so copying a link is a menu item and not a text selection; in a browser the hold is off entirely, since Safari and Chrome already answer that press. It is **not `<Hyperlink/>`** — that primitive is an `inline-flex` box sized to its content and a long URL would push the card wide rather than wrap, which is the second exception to the Hyperlinks rule. See the "Links out of the app" section of `native-architecture.md`.
- **A video is a link a post carries, and what the feed draws is the still.** `MediaKind.YOUTUBE` is a `PostMedia` row beside the photos and the attachment, so a video needed no column, no table and no discriminator — the kind names the provider rather than saying `VIDEO`, because a second source would then be another value rather than a nullable `provider` on every row that already exists. **The pasted address is parsed and thrown away**: `youtubeId` in `lib/utils.js` reduces the six shapes a person could plausibly paste (the watch page, `youtu.be`, `/embed`, `/shorts`, `/live`, `/v/`) to eleven characters, the row is written from `youtubeWatchUrl` of that, and every URL downstream (the poster, the player) is rebuilt from the id. That is what stands in for the ownership check every other media URL passes in `createPost` — an upload is trusted because it landed in a folder this group's grant created, and a video is trusted because nothing but a video id survives the front door. It is the one kind exempt from `isOwnedUrl`, and the only one. **The card holds a poster and a button, not an iframe**: a player per card is a megabyte of somebody else's JavaScript per card, running before anybody said they wanted to watch anything, so `<Video/>` mounts the frame on the press that asks for it and the press is the play (`autoplay=1`, because a stopped player under a finger that already pressed play asks twice). It is also the privacy measure, and a better one than the `youtube-nocookie.com` domain it replaced: nothing at all is requested from YouTube until a person presses play, where the privacy-enhanced domain still loaded the player for everybody who saw the card **and** was answered with "Sign in to confirm you're not a bot", because withholding the visitor cookie is what YouTube's abuse systems read as automation. **Photos or a video, never both** (`MAX_POST_VIDEOS`), because `<PostModal/>` and `<PostSlide/>` are each built around a single media box, so the second thing would be rows written and never drawn; the composer disables one control when the other is used and says why, and `createPost` refuses it either way. Tapping the still in the feed **plays** rather than opening `/p/:id` — a photo's tap opens the post because there is more of the photo to see, and a video's tap has an obvious answer of its own. On native, `server.allowNavigation` carries `www.youtube.com` so Android does not mistake the player's subframe for somebody leaving the app — which also means a YouTube link in a post body opens inside the WebView rather than in the phone's browser, the standing cost of that entry. **iOS cannot be the embedder at all**: its WebView origin is `capacitor://localhost`, YouTube refuses a non-http(s) embedder with error 153, and no `iosScheme` can help because WebKit reserves the only two schemes that would (Capacitor discards the value and keeps the default, silently). So there the app points its iframe at `public/embed.html` — a page served by our own deployment that holds the player, so YouTube sees an ordinary web origin embedding it. The scheme is all it wanted, not a public domain: the page works from a LAN dev server over cleartext http exactly as it does from the deployed site. A file rather than a route because it must inherit no layout, no providers and no auth gate; its URL comes off `API_BASE`, so a subpath deploy needs nothing new; and it repeats its own `allow`, because permissions delegate one frame at a time and autoplay would otherwise stop at it. Both are in "Links out of the app" in `native-architecture.md`.
- **Slide routes are shallow history.** Opening a post changes the URL with `history.pushState` so the feed behind it stays mounted; dismissing is `history.back()`, which is also why Android's back button works on it for free. `/p/:id` and `/notifications` are both one, and both are built from `<SlideSurface/>` + `useSlideDismiss()` rather than from their own copies of that behaviour. They **stack** — a notification opens the post it is about *over* the list, and back uncovers the list — which is why `openedStack` is a list of paths and what is open is derived from the URL rather than mutated on navigation. See the Slide routes section of `frontend-architecture.md`.
- **Notifications are per person, not per group — the one read in the app that is not scoped to the selection.** A like on your post or comment, a comment on your post, somebody following you, or a new post from an admin of a group you belong to, writes a `Notification` row in the same transaction as the event itself, so the two cannot drift; the bell counts unread and clears when the panel opens. A follow is the one kind that happened inside no post, so `Notification.postId` is nullable, both reads carry a `postId IS NULL` arm, and the row opens the follower's `<ProfileCard/>` rather than a slide route — and carries a **Follow back**, whose state rides in on the actor block from a filtered relation the panel's one query already joins. The bell lives in the desktop nav rail as a popover and at the top right of the mobile feed as a slide route, and both render the same `<NotificationList/>`. See the header of `src/lib/server/notifications.service.js`, which also carries the game plan for grouping ("and 9 others").
- **Push is Firebase, native-only, and changes none of that — the row is the notification, a push is one delivery of it.** A device that was asleep or was never granted permission finds the same rows in the panel, so nothing in the app depends on a delivery having succeeded and the whole feature is inert when `FCM_*` is unset. The sends run **after** the transaction that wrote the row commits (a push for a rolled-back write cannot be recalled) and are **never awaited** by it (a like must not fail because Google is having a bad minute), and cost one query each — the actor's name and the group's name are already in hand from `requireViewer`. `@capacitor-firebase/messaging` rather than `@capacitor/push-notifications`, because the official plugin hands back an *APNs* token on iOS and would mean two senders, two credentials and a `provider` discriminator on every row. The server talks FCM HTTP v1 directly with `jose` rather than through `firebase-admin`: FCM retired its batch endpoint, so `sendEachForMulticast` is itself one request per token and the dependency buys no round trip. **Not topics** — a topic subscription lives in Firebase rather than in the database, so a revoked member would keep receiving a parish's pushes, which is exactly the drift `Membership.status`-on-every-request exists to prevent. Setup steps are in the Push notifications section of `native-architecture.md`.
- **`RUNTIME_ROUTES` is the mechanism, and it is separate from how a route presents.** A runtime route is a real, shareable URL whose dynamic segment could not have been known at build time — `output: "export"` demands `generateStaticParams` for every dynamic segment, and a cuid from a live database does not exist when the bundle is built. So these have **no page file**: they are reached by shallow history navigation (`pushRoute` → `history.pushState`, which the App Router reflects through `usePathname()` without touching the segment tree) and resolved from the *pathname* against the registry. `runtimeRouteFor` is the primitive; `RUNTIME_SURFACES` in `components/RuntimeRoute.jsx` maps a prefix to what it draws. Adding one is two lines and no route file.
- **Three presentations over that one mechanism.** `slide: true` is the overlay — the base stays mounted and is pushed, the page transition is suppressed, the nav stays lit on the base, `<SlideRouter/>` animates the stack (`/p/:postId`, `/notifications`). `slide: false` is an ordinary page that cross-fades like any other route, substituted into the shell's page slot by `<RuntimeRoute/>` and reached with `pushRoute` (`/events/s/:sheetId`). `inline` is the third and the one that is both: a `slide: true` route that presents as a page above the `md` breakpoint, because the surface it would cover has room to hold it (`/inbox/c/:id`). `useRuntimePage` resolves that case into the page slot and `useRouteOpener` picks the opener, so no caller has to know which size it is in. **Everything overlay-flavoured keys off `slideRouteFor`, not `runtimeRouteFor`** — that is what stops a page inheriting an overlay's semantics, and registering a place as an overlay is visible: it cross-fades the route you came from out and back in *underneath* the sheet arriving over it.
- **Two settings trees, deliberately the same shape.** `/settings` asks about the person — picture, vocation, name, the two follow tallies, then **Info**, **General**, **About** and **Log out**. **About** is the one row on either list that is not about its subject: the mark on its launcher field, the version and build the reader is holding (inlined by `next.config.mjs`, since a static export inside a WebView has no process to ask and package.json cannot reach the client bundle), and who made the app. It is in the account tree because that is where a person looks for a version number before writing to support. `/group` asks the same shape about a parish — picture, name, *your role in it*, then **Info** and **Users** — and it is a sibling rather than a branch, because a group is not a setting of yours: your standing in it can change, you can be removed from it, and the tree is admin-only where the account's is everyone's. Both are drawn by the shared `<SettingsRow/>`, so a reader who has used one already knows how to read the other. The account surface's picture opens the viewer's own `<ProfileCard/>` (the badge is `arrow_outward`, because it opens *over* rather than further *in*); the group surface's picture goes to the feed, which is the same gesture — show me the public face of this subject.
- **The account surface *is* `/settings` — the index of the account tree, not a sibling of it — and `/settings/general` and `/settings/info` hang off it.** One list rather than a nav popover plus a tab rail, which would express the same handful of destinations twice and which a phone has no room for; being the index is what makes each sub-page's back arrow point at its real parent. The avatar in the nav is that tree's tab and stays lit across all of it, because `isRouteActive` is a segment-safe prefix test. Nothing here is about a group — no check, no role, no roster; all of that is `/group`, gated once in its layout. The group form is `react-hook-form` + zod through the `Form` primitives like every other, `slug` and `kind` stay uneditable (the slug is the seeds' natural key, `kind` sits above a parish admin), and deleting is the danger zone at the foot of `/group/info`, armed only once the group's name is typed and gated on the server-composed `canDelete` — see §11 of `backend-architecture.md`. **The switcher is still the only way into the group tree** — a gear revealed on row hover on desktop, a `<HoldMenu/>` long-press on mobile — and it *selects* the group on the way in, which is what lets all three pages be static routes with no id in the URL.

Full patterns and conventions: `.claude/skills/develop/frontend-architecture.md`. The API contract and server layer: `.claude/skills/develop/backend-architecture.md`.

## Development Commands

```bash
npm install              # install deps (runs `prisma generate`)
npm run dev              # Next dev server at :3000
npm run build            # production build → .next/
npm run start            # serve the production build
npm run lint             # eslint (max-warnings 0)

npm run build:native     # static export → out/ (the bundle Capacitor ships)
npm run sync             # build:native + cap sync (push assets into android/ and ios/)
npm run ios              # sync + open Xcode
npm run android          # sync + open Android Studio
npm run open:ios         # open Xcode against the last sync (no rebuild)
npm run open:android     # ...same for Android Studio — one sync serves both platforms

npm run release:android            # build + sign an .aab and publish it to the Play internal track
npm run release:android -- --dry   # ...build and sign only, upload nothing (prints the path)
npm run release:android -- --track alpha --draft --notes "..."
npm version patch                  # the version bump — Gradle reads package.json

npm run db:up            # start the local dev Postgres (docker-compose.yml)
npm run db:down          # stop it, keeping the data
npm run db:nuke          # stop it and delete the volume

npm run prisma:generate  # regenerate the Prisma client from the schema
npm run prisma:migrate   # create/apply a dev migration (uses DIRECT_URL)
npm run db:secure        # RLS + revoke Data API grants — after EVERY migration
npm run db:seed          # DEV seed: two groups, a roster, the post corpus
npm run db:seed:prod     # PROD seed: one group, two admins, no posts
npm run db:reset         # DESTRUCTIVE: drop, re-migrate, re-secure, re-seed
npm run prisma:studio    # open Prisma Studio

npm run storage:setup    # create/reconcile the "media" Storage bucket — once per environment

npm run comments:rescore          # recompute every comment's rank — after re-tuning src/lib/rank.js
npm run comments:rescore -- --dry # ...report what would change, write nothing

npm run crypto:test               # exercise X3DH + the Double Ratchet — after any change in src/lib/crypto

npm run signups:remind            # send every sign-up reminder that has come due
npm run signups:remind -- --url https://throughgrapevine.com/api   # ...against a deployment

npm run owner                  # list every platform owner and the groups they created
npm run owner -- a@parish.org  # grant OWNER (provisions the account if the address is new)
npm run owner -- --revoke a@parish.org   # take it back; their groups are left alone

npm run dev:login              # print a sign-in link for the seeded admin (no email sent)
npm run dev:login -- member    # ...or the seeded member

npm run reviewer                                  # list store-review accounts and their access
npm run reviewer -- a@x.org --org <slug>          # provision one as an APPROVED MEMBER
npm run reviewer -- a@x.org --revoke              # take its access away after review

npm run erase -- a@x.org                          # right-to-erasure: report, change nothing
npm run erase -- a@x.org --confirm                # ...actually destroy the account
```

`dev:login` mints the same verification token through the Admin API and prints it — both the
link and the code — rather than mailing it. It needs no inbox at all, which is what makes it
the way to sign in **on a device**, and it consumes none of the hourly email quota. Local
script only — the secret key it needs must never sit behind a route.

Seeding provisions two real sign-innable accounts from `SEED_ADMIN_EMAIL` (Priest, ADMIN)
and `SEED_MEMBER_EMAIL` (Faithful, MEMBER), so both sides of the permission model can be
demonstrated. Everyone else is a profile with no credentials.

Seeding is never automatic — the CLI does not run it after a migrate. `db:reset` passes
`--skip-seed` on purpose, because the seed has to land *after* `db:secure`. And
`prisma migrate reset` is blocked for AI agents without explicit consent; that guard is
correct, so run a reset yourself rather than asking an agent to work around it.

## Deploying

**The API runs in the database's region, and `vercel.json` is the only thing saying so.** Supabase is in `us-east-2`, and a function left to Vercel's default lands in `iad1` — which puts a cross-region hop in front of the function and a second one between the function and Postgres, on a server written to count round trips. `cle1` *is* us-east-2: pinning it there puts the function beside both the edge that received the request and the pooler it queries. Delete the file and nothing breaks visibly, which is exactly why it is written down here.

**Web** is the Node build: `npm run build`, then `npm run start` (`next start`) to self-host. This is the target that serves `/api`, and it's also what makes `/p/:id` deep links work. On Vercel the same build's route handlers run as **serverless functions** rather than as that one long-lived server, which is what decides the pooler above — read it before setting `DATABASE_URL` on a deployment. It requires `DATABASE_URL`, `DIRECT_URL`, `NEXT_PUBLIC_SUPABASE_URL`, and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`; `SUPABASE_SECRET_KEY` is only needed for seeding and invites, and must never be exposed to the client. Set `NEXT_PUBLIC_BASE_PATH` only if serving under a subpath. See `.env.example`.

**Native** ships from the static export: `npm run ios` / `npm run android` builds `out/`, syncs it into the native project, and opens the platform IDE to archive from there. Re-run `npm run sync` after any web change — the native projects hold a copy of `out/`, not a live reference. The export contains no API, so a native build needs `NEXT_PUBLIC_API_BASE_URL` pointing at a deployed instance. The Supabase URL and anon key are inlined at build time too, so re-sync after changing either.

**Android releases are one command, and the version is `package.json`.** `npm run release:android` builds the export, syncs it, assembles a signed `.aab`, and drives the Play Developer API — `edits.insert` → `bundles.upload` → `tracks.update` → `commit` — with the edit deleted on any failure, so a half-finished release is never left in the console. The access token is a service-account JWT signed with `jose`, the same few lines `src/lib/server/push.js` already runs against FCM; `fastlane` would do this in Ruby, and a Gemfile is a lot to introduce for four HTTP calls. **Nothing in the release path writes a tracked file**: `android/app/build.gradle` *reads* `package.json` and derives `versionCode` from the semver (`0.1.0` → `100`, two digits each for minor and patch, asserted at configure time), so `npm version patch` is the entire bump and an interrupted run leaves the tree clean. Signing comes from the untracked `android/keystore.properties` or `GRAPEVINE_STORE_*`/`_KEY_*`, and is declared **only when all four values are present** — a checkout without the keystore still configures, still builds, and is merely unsigned, which is what keeps CI and Android Studio working. Refusing to *ship* that is the script's job, not Gradle's. Both preflight checks run before the build rather than after it: `scripts/release-target.mjs` is `db-target.mjs` one layer out, rejecting a `NEXT_PUBLIC_API_BASE_URL` that is cleartext or a private address, because that value is inlined into the bundle and cannot be corrected without another upload — `ALLOW_INSECURE_API=1` is the deliberately ugly override for a device test. `--dry` stops after signing and prints the path, which is also how the **first** submission has to go: `edits:commit` cannot create a listing, so the store entry, content rating and Data safety form are one-time console work and the API only takes over from the second upload.

> `build:native` overwrites `.next` with the export, so `npm run start` afterwards serves a build with no `/api`. Re-run `npm run build` before `npm run start` if you've built native in between. `next dev` is unaffected either way — it builds into `.next-dev`, so a build of either target can run while it stays up.
